# Reproducible core language matrix

Date: 2026-07-18

## Result

The pure-PBLang runner produced 24 rows: 22 passed correctness and resource
measurement, 2 were explicitly unavailable because Zig is not installed, and
0 failed. This report does not combine unlike measurements into an aggregate
score and does not claim that PBLang is the fastest language.

The focused benchmark contracts passed, followed by the complete canonical
semantic suite: 689/689 passed, 0 failed/ignored/filtered, in 205.21 seconds
with 1,801,672 KiB whole-runner peak RSS. The clean complete 24-row matrix
finished in 16.06 seconds with 95,236 KiB process peak RSS. It was rerun only
after the graph update and other benchmark processes had finished, avoiding
known CPU and storage contention.

Host:

- Intel Core i7-1195G7, 8 logical CPUs
- PBLang 0.5.7
- fixed integer kernel: 1,000,000 iterations, checksum `474518`

Toolchains present: PBLang interpreter, PBLang hosted C99, PBLang direct x86-64

Python 3.12.3, and Node.js 18.19.1. Zig was not installed.

## Method

- Every language receives a fixed source fixture from an internal registry.
  Callers cannot inject a command or arbitrary foreign source.
- Compiled rows use release optimization, disabled debug information, and
  stripped symbols where supported. The PBLang C99 row measures the complete
  `pblang transpile` plus native C compiler pipeline.
- The PBLang direct-codegen row runs the fixed PBLang driver
  `bench/drivers/repro_codegen_x64.sapp`, imports the PBLang-written
  `stdlib/native/codegen_x64.sapp`, safety-certifies the generated bytes,
  validates the ELF header, writes the artifact, and marks it executable without
  a shell. Compile latency includes driver startup/imports, code generation,
  validation, write, and `chmod`.
- Compilation records one first/cold sample and three warm samples. Execution
  records one first/cold sample, discards one warm-up, and retains seven warm
  samples.
- Every execution must emit the exact expected checksum. Timeout, nonzero exit,
  missing output, or wrong output rejects the row.
- Wall time comes from the parent monotonic clock. GNU `time` records user and
  system CPU time and Linux peak RSS in KiB. The report preserves all raw
  samples and reports median and interpolated p95.
- Cold means the first invocation in this run. It does not mean rebooted,
  filesystem-cache-dropped, or CPU-frequency-fixed. Results are local evidence,
  not universal machine-independent constants.

## PBLang findings

- PBLang direct x86-64 codegen is 1.337x slower than C on this integer fixture,
  while its complete measured compile path is 3.005x slower. Its 487-byte ELF
  is 96.6% smaller than the 14,472-byte C artifact. Relative to PBLang C99, the
  direct executable is 2.870x faster, its measured compile path is 2.280x
  faster, and its artifact is 97.9% smaller. These results identify the direct
  backend as the strongest current PBLang native path for this supported subset;
  they do not establish whole-language or whole-application superiority.
- PBLang C99 is 3.836x slower than C on this integer fixture and its end-to-end
  warm compile is 6.851x slower. Its 22,664-byte artifact is 1.566x the C
  artifact. The next optimization work should profile generated modulo/numeric
  semantics and separate transpiler, C emission, C compilation, and link phases.
- The PBLang interpreter is 2.194x slower than Python and 3.605x slower than
  Node.js on the kernel, although its process startup and peak RSS are lower in
  this run. The likely targets are numeric opcode specialization, loop dispatch,
  and dynamic-value overhead; those causes require phase profiling before a
  code change is accepted.
- PBLang C99 startup is within this run's process-noise range of C and Go, but
  one microbenchmark is not evidence for application startup generally.

## Comparability boundaries

- Java `.class` and Mono assembly sizes are not self-contained native binary
  sizes. Go and Rust include different runtime/linkage choices. Artifact bytes
  are reported, but cross-runtime storage conclusions require deployment bundle
  measurements.
- The C99 compile row includes both PBLang transpilation and C compilation;
  direct C/C++/Rust/Go rows begin from their language source. This is an honest
  end-to-end latency comparison, not a same-phase compiler comparison.
- The direct-codegen row supports the source subset accepted by
  `stdlib/native/codegen_x64.sapp` and produces Linux x86-64 ELF artifacts. It
  is unavailable on non-Linux or non-x86-64 hosts. The reported compile time is
  intentionally end-to-end and therefore includes PBLang process startup and
  module loading; a future same-process phase benchmark should complement it.
- GNU `time` exposes CPU time with coarse resolution for very short processes,
  so several startup/kernel CPU medians round to zero. Wall medians remain
  monotonic-clock measurements.
- The fixed checksum prevents dead-output elimination in the observed builds,
  but the fixture remains a microbenchmark. It does not represent GUI, server,
  database, accelerator, or whole-application performance.

## Coverage ledger

Runnable here or in an existing correctness-gated PBLang harness:
compilation, startup, execution, memory, artifact size, CPU utilization,
algorithms/data structures, polyglot calls, interpreter, and native code.

Partial and not presented as equivalent cross-language evidence: multicore
scaling, filesystem I/O, mathematical breadth, concurrency, GUI rendering,
latency, and FFI overhead.

Not yet comparable because an equivalent contract is missing: network I/O,
JSON processing, web-server throughput, and database operations. GPU/parallel
rows are conditional on a registered equivalent kernel runtime. The runner
emits all 24 statuses and reasons before the measurements so missing categories
cannot be mistaken for completed benchmarks.

## Reproduce

From the pblang repository root:

```sh
./target/release/pblang bench/reproducible_core_matrix.sapp --allow-all
```

The runner requires GNU `time` and `timeout`. Install additional compilers to
turn their explicit `unavailable` rows into measured rows, then rerun the same
command without changing the fixtures.

Run only the direct-codegen example with:

```sh
./target/release/pblang examples/repro_codegen_benchmark/main.sapp --allow-all
```
