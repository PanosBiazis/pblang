# pblang benchmarks

## Pure-PBLang reproducible competitor core

The bounded competitor runner compares the PBLang interpreter, hosted C99, and
direct Linux x86-64 codegen paths with C, C++, Rust, Go, Java, C#/Mono, Python,
JavaScript/Node.js, and Zig when their local toolchains are available:

```sh
./target/release/pblang bench/reproducible_core_matrix.sapp --allow-all
```

It records one first/cold compile and run, three warm compiles, one discarded
runtime warm-up, seven warm executions, median/p95, raw samples, peak RSS, CPU
utilization, release artifact size, toolchain/environment metadata, and an exact
checksum. Missing toolchains remain explicit `unavailable` rows. The runner and
fixed source registry are implemented in `stdlib/repro_benchmark.sapp`; callers
cannot inject foreign commands or arbitrary source.

The direct-codegen row executes an ELF generated by
`stdlib/native/codegen_x64.sapp`; it never routes through C99. Its complete
compile metric includes PBLang driver startup/imports, safety certification,
ELF validation/write, and executable permission setup. Run its small working
example independently with:

```sh
./target/release/pblang examples/repro_codegen_benchmark/main.sapp --allow-all
```

The verified local baseline is
[`results/2026-07-18-reproducible-core-matrix/REPORT.md`](results/2026-07-18-reproducible-core-matrix/REPORT.md).
It reports measured PBLang gaps and comparability boundaries instead of an
aggregate winner score. The general protocol is in
[`docs/Benchmarking.md`](../docs/Benchmarking.md).

The subsequent range-proven constant-division optimization, its before/after
measurement, 19-sample C/C++/Rust/Go comparison, refreshed core matrix, and raw
data are recorded in
[`results/2026-07-18-x64-constant-div/REPORT.md`](results/2026-07-18-x64-constant-div/REPORT.md).
Run that focused suite with:

```sh
./target/release/pblang run bench/x64_const_div_benchmark.sapp --allow-all
```

The next measured bottleneck slice separates direct compiler startup/import,
emission, uncached publication, and verified artifact-cache hits; compares the

```sh
./target/release/pblang bench/c99_modulo_stages.sapp --allow-all
```

Raw samples, the refreshed competitor matrix, correctness evidence, and

The next slice addresses repeated self-hosted module compilation and

`pbide_surface_manifest_stages.sapp` correctness-gates and measures the shared
target-aware PBIDE action/panel projection plus Web renderer compilation. It
reports warm in-process median/p95 separately from cold process startup and
locked-module verification.

`linux_process_stages.sapp` measures the complete warm supervised-process path,
including generation of argv/supervisor ELF images, private-directory setup,
launch, wait, bounded output loading, process-group verification and cleanup.
It does not report compiler startup or module-import time as subprocess latency.

The first measures tokenize, parse, tree interpretation, and direct x86-64
generation. The second compiles once and averages five executions on the
self-hosted bytecode VM. The third correctness-gates and times common and
late-name builtin dispatch; run several fresh pinned processes and compare
medians. None of these fixtures is a substitute for application benchmarks.
The accepted 2026-07-13 A/B evidence is under
`results/2026-07-13-selfhost-vm-builtins/`.
The fourth benchmark alternates annotated and allocation-fallback bytecode in
the same process, controlling for startup and CPU-frequency drift. Accepted
direct-call descriptor samples and separate peak-RSS processes are under
`results/2026-07-13-selfhost-vm-direct-builtins/`.
The fifth fixture correctness-gates recursion, an arithmetic loop, and common
builtin loops while measuring VM opcode-dispatch ordering. Its accepted
median-of-seven A/B evidence and rejected interpreter experiments are under
`results/2026-07-14-selfhost-vm-dispatch/`.
The tree-interpreter fixture separates preparation, repeated AST execution, and
end-to-end compile-and-run timing across one-argument recursion, two-argument
recursion, and closure capture. Prepared numeric AST/operator/call metadata was
accepted against seven fresh CPU-pinned processes; evidence is under
`results/2026-07-14-tree-interpreter-tags/`.
Prepared block bodies and declaration bits now remove repeated scope scans from
`if`/`elif`/`else`/`while`. Two A-B-A-B rounds show 5.63-8.12% lower `fib18`
execution and 5.40-6.14% lower `choose(15,7)` execution. Evidence and the
separately rejected shared return-signal experiment are under
`results/2026-07-14-tree-interpreter-scope-cache/` and
`results/2026-07-14-tree-interpreter-return-signal/`.
The lexical-cache fixture uses longer batches and paired same-process lookup
controls for depths 0, 1, and 2. Identifier nodes resolve their immutable
lexical depth once; subsequent reads and assignments index that scope directly.
The control fixture correctness-gates recursive returns, returns through nested
lexical scopes, and allocation-heavy break/continue loops. The closure-layout
fixture alternates map and fixed-array metadata reads in one process and reports
five-sample medians, isolating representation cost from recursive-call noise.
The builtin-resolution fixture alternates a controlled dynamic-scope AST with
the accepted statically unshadowed path. It covers `len`, `map_has`,
`str_starts_with`, and a mixed workload; seven fresh pinned-process results,
compile overhead, resource evidence, rejected experiments, and limitations are
under `results/2026-07-17-tree-interpreter-builtin-resolution/`.
The self-hosted typecheck fixture correctness-gates malformed AST and resource
budgets, then reports legacy-compatible, typed-signature, and deterministic
diagnostic workloads separately. This keeps the cost of stronger checking
visible instead of comparing a shallow legacy pass with a full semantic walk.
The type-system fixture measures recursive generic-type parsing, valid typed
struct/enum checking, and deterministic invalid-payload plus exhaustiveness
diagnostics. It reports average, p50, p95, min, and max from separate samples;
the parser fixture deliberately reuses immutable tokens to guard against state
leaking between compilations.
The VM call fixture separately gates recursive unary, zero-argument, and
two-argument closure workloads. Only the measured two-argument fixed-shape
path is specialized; zero/unary and generic calls retain their old path.
Current evidence is under `results/2026-07-14-interpreter-vm-cache/`.
The x86-64 linear-recurrence fixture compares the exact proven direct emitter
with a fold-equivalent control and checks both `fib(36)` and `fib(92)`. Its
seven-process execution A/B, 30-sample codegen measurements, artifact/RSS
metrics, proof boundary, and rejected generic rewrite are under
`results/2026-07-14-x64-linear-recurrence/`.
The self-hosted C99 fixture measures complete hosted translation-unit
generation, speed/size/portable compiler profiles, executable size, bounded
execution, and verified `fib(32)` for normal f64 semantics plus explicit integer
semantics. It also reports bounded module-link time, linked-source size,
linking-excluded C99 lowering, linked executable size, and verified native
cross-module global/closure runtime. The project fixture includes dependency-
ordered constants, a global closure handle, and module-global definition counts.
The shootout reports these rows separately from
the reference CLI C99 transpiler.

The latest broad local comparison is
`results/2026-07-14-interpreter-compact-closures/competitors/`. It includes recursive-call and
register-loop runtimes, artifact size, peak RSS, compiler pipeline phases, and

## Cross-language category matrix

`language_category_matrix.sapp` compares the same correctness-gated fixtures
across 15 runtime definitions: pblang, Python, JavaScript, Ruby, Perl, Lua, PHP,
Tcl, AWK, Bash, R, Julia, Raku, Dart, and Swift. It measures six separate
surfaces instead of collapsing them into one score:

- process startup;
- recursive function calls (`fib(22)`);
- integer loops and modulo arithmetic;
- array construction and traversal;
- repeated string growth;
- hash-map insertion and lookup.

Run it with:

```sh
target/release/pblang run bench/language_category_matrix.sapp --allow-all
```

Each installed runtime gets one warm-up and three measured subprocess samples.
The stable pipe-delimited output includes median, average, minimum, maximum,
interpolated p90/p95/p99, standard deviation, MAD, IQR, coefficient of
variation, IQR outlier count, a stability classification, checksum, and every
raw sample. Missing runtimes remain explicit
`unavailable` rows. A timeout, nonzero exit, or wrong checksum fails the suite.
Wall time includes process startup; this matrix therefore complements rather
than replaces the compiled-language, artifact-size, peak-RSS, compiler-phase,
polyglot, and native-backend benchmarks already in this directory.

The generators and runner are implemented in pblang in
`stdlib/language_benchmark.sapp`. The shell competitor suite only preserves
environment metadata and raw output.

## Benchmark quality and regression budgets

`stdlib/benchmark.sapp` provides the robust statistics used by the language
matrix. `stdlib/performance_budget.sapp` adds fail-closed multi-metric gates for
latency, peak RSS, artifact/storage size, throughput, or caller-defined numeric
metrics. Missing/non-numeric values, invalid budgets, and changed zero
baselines fail instead of silently passing.

Run the deterministic statistics and budget-overhead fixture with:

```sh
target/release/pblang run bench/benchmark_quality_stages.sapp --allow-all
```

The fixture proves accepted and rejected budgets before reporting stage cost.
It is itself written entirely in pblang.
The accepted 2026-07-15 evidence is recorded in
`results/2026-07-15-benchmark-quality-ir-copy/REPORT.md`.

`ecosystem_vertical_stages.sapp` prevents isolated micro-optimizations from
hiding integration cost. It correctness-gates and measures a complete
pblang-only path through a one-action CLI/native-GUI/Web app, hardened Web
preview, four-metric regression contract, product-health release gate, and
secure polyglot plan. `app_facade_stages.sapp` separately reports the universal
app constructor beside the lower-level CLI/GUI/Web adapters.

## Platform/ABI emulation matrix

`platform_emulator_matrix_stages.sapp` exercises the pblang-only bounded
userspace model for Linux, Windows, macOS, Android, iOS, FreeBSD, and WASI over
x86/x86-64, ARM, RISC-V, MIPS, PowerPC, SPARC, and WASM profiles where valid.
It separately measures profile resolution, virtual path normalization, bounded
memory, and portable syscall dispatch:

```sh
target/release/pblang run bench/platform_emulator_matrix_stages.sapp --allow-all
```

The catalog also covers bounded OpenBSD, NetBSD, Solaris/illumos, and Haiku
userspace profiles. Large virtual memories use a sparse, logically zero-filled
layout by default; small memories retain contiguous-array behavior. The matrix
reports controlled 1 MiB contiguous versus sparse construction stages alongside
read/write correctness.

This is an OS/version/ABI contract layered over the checked ISA execution
models. It is not presented as complete kernel, driver, GUI-framework, or
proprietary OS emulation.

## Direct x86-64 constant division benchmark

Run the checksum-gated integer kernel against direct PBLang x86-64 codegen and
the available C, C++, Rust, and Go toolchains:

```sh
./target/release/pblang bench/x64_const_div_benchmark.sapp --allow-all
```

## Language shootout — `bench/lang_shootout.sh [N]`

Naive recursive `fib(N)` (raw arithmetic + function-call overhead) across pblang
(native + interpreter) and mainstream languages. Each target is skipped if its
toolchain is absent. Reports wall-clock ms (incl. process startup), the result
(all must match), and on-disk size for compiled targets.

`N` is embedded in each generated source fixture. Consequently this category
also measures constant propagation, recursion transformation, and other compiler
specialization opportunities; it is not a pure runtime-input call benchmark.
Results such as Fortran's very low fixed-input time must be interpreted within
that boundary. A future runtime-input category requires an equivalent argument
or stdin API in every backend, including direct machine-code targets.

### fib(36) — compute-dominated (this machine: x86-64, gcc 13, rustc 1.94)

| target                | time_ms | result    | size    |
|-----------------------|--------:|-----------|--------:|
| C (gcc -O2)           |      22 | 14930352  | 16 KB   |
| Rust (rustc -O)       |      34 | 14930352  | 3.9 MB  |
| Java (OpenJDK 17)     |      73 | 14930352  | —       |
| **pblang (native/C99)** | **117** | 14930352 | **25 KB** |
| Node.js (V8)          |     199 | 14930352  | —       |
| Python 3 (CPython)    |    1413 | 14930352  | —       |
| pblang (interpreter)  |    8363 | 14930352  | —       |

**Takeaways:** pblang's native target beats Node.js (1.7×) and Python (12×), trails
Java by ~1.6× and C/Rust by ~3–5×, and is **~71× faster than the pblang interpreter** —
while producing a **25 KB** static binary (vs Rust's 3.9 MB). Numbers vary by machine;
re-run `bench/lang_shootout.sh 36` to reproduce.

## Direct machine-code target — `stdlib/native/elf_x64.sapp`

Proof that pblang can target the machine *with no other language in the codegen path*
(no C, assembler, or linker): `elf_x64.sapp` is pure pblang that writes the raw bytes of
a runnable Linux x86-64 ELF executable — ELF/program headers + hand-encoded x86-64
instructions (`write(1,msg,len); exit(code)`). Emitting it from a **native-compiled**
pblang binary and running the result prints its message and exits 42 — verified. This is
the foundation for a full pblang-written backend (more ISAs / OS formats to follow).

## pblang-written code generator — `stdlib/native/codegen_x64.sapp`

A pblang compiler that lowers whole imperative programs (variables, `if`/`while`, comparisons,
arithmetic, `return`) to x86-64 machine code via a CPU-stack machine — driven by the self-hosting
parser. **Native-speed, measured:** the same 100-million-iteration nested loop runs in **156 ms** as
pblang-generated machine code vs **18 630 ms** through the pblang interpreter — **~120× faster**,
~1.5 ns/iteration (native CPU tier). Non-optimizing today (no register allocator), so it matches
`-O0` C; a regalloc + peephole pass closes the gap to `-O2`/Java. This is the path to "beat Java/C"
and to replacing the Rust C-transpiler entirely.

**Functions + recursion (System V ABI), optimized.** `compile_fns(src)` compiles whole programs with
user functions and recursion (immediate-operand folding + a register-oriented result-in-`rax` pass).
`fib(32)` — pblang's own pblang-written code generator vs the field, on this machine — measuring
**file size** (`stat`), **peak RAM** (RSS via `/usr/bin/time -v`), and **wall-clock time on this CPU**
(includes process startup; ms resolution is coarse, so small numbers carry ±1–2 ms fork/startup noise;
no GPU/VRAM — these are CPU benchmarks):

| target | file size | peak RAM (RSS) | time |
|--------|----------:|---------------:|-----:|
| **pblang-codegen (machine code)** | **442 B** | **264 KB** | 8 ms |
| C (gcc -O2) | 15.8 KB | 1132 KB | 5 ms |
| pblang interpreter | — | 8700 KB | 789 ms |
| Python 3 | — | 10 548 KB | 219 ms |
| Java (JVM) | — | 38 544 KB | 27 ms |

pblang's native output is **smallest on disk (35× < C) and lowest RAM (264 KB — 4× < C `-O2`, 33× <
the interpreter, 146× < the JVM)**: it is statically linked with **no libc** (raw syscalls), carrying
none of libc's ~1 MB footprint. On **time** it beats Java/Node/Python/interpreter and trails only
C/Rust/Fortran on this workload. Structurally proven tail recursion modulo addition now reuses the
current frame for the right recursive branch. The longer `fib(36)` stress run has a five-sample
median of **45 ms**, peak RSS **264 KB**, and exact result `14930352`; unlike the 8 ms `fib(32)` row,
it is less dominated by process startup. Verified recursive results include `fib(10)=55`,
`fib(13)=233`, `fact(5)=120`, and `g(6,8,7)=41`. No C, Rust, assembler, or linker is in the direct
code-generation pipeline.
